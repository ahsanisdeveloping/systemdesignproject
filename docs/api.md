# Phase 1 CRUD API

Express lives in `app/api`; the schema lives in `apps/api/sql/001_initial_schema.sql`.
This change requires no new migration. Start PostgreSQL, then run:

```powershell
cd E:\grind\systemdesignproject\app\api
npm.cmd run dev
```

Base URL: `http://localhost:5000/api/v1`, or `http://localhost:8080/api/v1`
through Nginx. Browser clients use relative `/api/v1` URLs.

These are **unauthenticated local development management endpoints**. There is
no trusted user identity, role enforcement, or authorization-based tenant
isolation yet. Membership queries filter by organization, but any caller can
select that organization and manage members. Authentication and membership-based
authorization are required before public deployment. Roles are stored data at
this stage; removing the last owner is permitted by the initial design.

## Routes

Paths are relative to `/api/v1`.

| Resource | Collection path | Item path | POST body | PATCH fields |
| --- | --- | --- | --- | --- |
| Users | `/users` | `/users/:id` | `{"name":"Ahsan","email":"ahsan@example.com"}` | name and/or email |
| Organizations | `/organizations` | `/organizations/:id` | `{"name":"AlgoritX"}` | name |
| Memberships | `/organizations/:organizationId/members` | `/organizations/:organizationId/members/:userId` | `{"user_id":"<UUID>","role":"developer"}` | role |

Each collection supports **GET** (list) and **POST** (create). Each item supports
**GET** (read), **PATCH** (partial update), and **DELETE**. There are 15 operations.
Memberships are identified by the organization/user pair, not a separate ID.
Membership item queries always filter by both IDs. Nonexistent organizations
return 404, including for membership lists.

## Validation

POST and PATCH require `Content-Type: application/json` and a JSON object.
All POST fields shown above are required. PATCH requires at least one supported
field. Unknown/read-only fields and null values are rejected. IDs and timestamps
are generated by PostgreSQL and cannot be supplied or changed by clients.
Membership identity cannot be changed by PATCH.

Names are trimmed, nonblank, at most 200 characters, and exclude control
characters. Emails are trimmed and lowercased, have basic syntax validation,
and are at most 254 characters. Syntax validation does not verify ownership or
deliverability. Roles must be `owner`, `admin`, or `developer`. IDs must be UUIDs.

## Responses and pagination

POST returns **201**, `Location`, and `{"data":{...}}`. GET and PATCH return
**200** with the same data envelope. DELETE returns **204** with no body;
repeating a delete returns 404. Timestamps serialize as ISO 8601 UTC strings.

List routes accept only `limit` (default 20, range 1–100) and `offset` (default
0, range 0–1,000,000). Repeated/unknown query parameters are rejected. Ordering
uses creation timestamp and UUID. Offset pages can shift during concurrent writes.

```json
{ "data": [], "pagination": { "limit": 20, "offset": 0 } }
```

Pagination reports the requested page; there is no total count. Every response
has `X-Request-Id` and `Cache-Control: no-store`. Error responses contain:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [{ "field": "role", "message": "Must be owner, admin, or developer" }]
  },
  "requestId": "<request UUID>"
}
```

| Status | Meaning |
| --- | --- |
| 400 | Malformed JSON |
| 404 | Missing resource, membership pair, or route |
| 409 | Duplicate normalized email or membership |
| 413 | Body exceeds 100kb |
| 415 | Missing/unsupported JSON content type on a write |
| 422 | Invalid input, pagination, UUID, or foreign reference |
| 500 | Unexpected server error |
| 503 | Database connection failure, overload, or query timeout |

Parameterized queries keep values separate from SQL. Each write is one atomic
statement with RETURNING. Database uniqueness and foreign keys remain the final
authority, including for concurrent inserts. Deleting a user or organization
cascades to its memberships and preserves the other parent. SQL, constraint
details, credentials, and stack traces are not returned to clients.
Health endpoints retain their existing `{status,database,...}` response shape.

## PowerShell example

```powershell
$apiBase = 'http://localhost:5000/api/v1'
$createdUser = Invoke-RestMethod -Method Post -Uri "$apiBase/users" -ContentType 'application/json' -Body (@{ name = 'Test User'; email = 'test-user@example.com' } | ConvertTo-Json)
$createdOrg = Invoke-RestMethod -Method Post -Uri "$apiBase/organizations" -ContentType 'application/json' -Body (@{ name = 'Test Organization' } | ConvertTo-Json)
$membersUrl = "$apiBase/organizations/$($createdOrg.data.id)/members"
Invoke-RestMethod -Method Post -Uri $membersUrl -ContentType 'application/json' -Body (@{ user_id = $createdUser.data.id; role = 'developer' } | ConvertTo-Json)
Invoke-RestMethod -Uri $membersUrl
Invoke-RestMethod -Method Patch -Uri "$membersUrl/$($createdUser.data.id)" -ContentType 'application/json' -Body '{"role":"admin"}'
```

Use a fresh email or the existing user's ID when repeating this example.

## Verification

From `app/api`, run `npm.cmd test` and `npm.cmd run test:integration`.
The first suite uses real HTTP requests with a substituted database. Integration
tests use the PG environment settings, create a random test schema, apply the
migration there, exercise all CRUD operations, concurrent duplicates, constraints,
organization scoping, and both cascades, then drop only that test schema. The
database user needs schema creation/deletion privileges. Public tables are untouched.

[openapi.json](openapi.json) defines the CRUD contract for clients and frontend work.
Implementation references: [node-postgres queries](https://node-postgres.com/features/queries)
and [Express 5 error handling](https://expressjs.com/en/guide/error-handling/).
